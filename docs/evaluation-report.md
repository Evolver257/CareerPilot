# CareerPilot：检索对照实验与 Worker 可靠性验收

实测日期：2026-09-05。结论：已建立可复跑评测与故障注入测试，真实模型确实参与计算；V3 切块在同一冻结语料上明显改善了语义混合重排，但当前证据仍不支持“AI 已被证明在所有场景显著更好”。

## 1. 实验设计

- 只读访问系统已有 715 个岗位，按 JD 内容去重、过滤不足 120 字符的描述，再按内容哈希排序取 120 个；未修改真实岗位、简历或投递记录。
- 使用生产知识库切块器生成 545 个知识块。评测数据库为隔离的内存 SQLite。
- 36 个技能/岗位主题，每个主题有直接关键词和语义改写两种问法，共 72 题；另加 8 道无答案题，总计 80 题。
- 按主题拆分：开发集 24 题；测试集 48 道有答案题、8 道无答案题。同主题不跨集合。本轮没有根据测试集调参。
- 相关性由明确的关键词/正则规则生成，记录原始 JD 证据。这是 **silver 标注**，不是独立人工金标。支持人工审核后通过 `--labels` 重新评测。
- 五种方案使用相同岗位快照和标注；按岗位 ID 去重后评测前 5 个，不用重复知识块增加命中数。

固定快照 SHA-256：

```text
2e2e46d020b26c511c632ecb570e5c97339ac8c8182ed4d543f133f02410c6ef
```

## 2. 实测结果

下表为测试集。Recall/nDCG/MRR 对 48 道有答案题宏平均；延迟包含测试集全部 56 题，预热后测量，绕过检索结果缓存。

| 方案 | Recall@5 | nDCG@5 | MRR@5 | P50 | P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 词汇检索 | 0.0979 | 0.2487 | 0.2604 | 18.7 ms | 86.7 ms |
| 原 Hash 混合检索＋规则重排 | 0.1749 | 0.4477 | 0.5538 | 182.1 ms | 241.6 ms |
| 真实语义向量单路 | 0.1227 | 0.2919 | 0.4372 | 221.6 ms | 240.8 ms |
| 真实语义混合检索＋规则重排 | 0.1915 | 0.4303 | 0.5493 | 230.9 ms | 301.4 ms |
| 真实语义混合检索＋Cross-Encoder | 0.1826 | 0.4798 | 0.6361 | 3863.6 ms | 5269.1 ms |

解释：

1. 真实语义混合检索的 Recall@5 比原方案相对提高约 **9.5%**，但 nDCG@5 略降。因此不能简单用向量替换原检索。
2. 加入 Cross-Encoder 后，nDCG@5 相对原方案提高约 **7.2%**，MRR@5 提高约 **14.9%**，说明相关岗位更靠前；代价是 CPU P95 约 **5.27 秒**。
3. 在 24 道语义改写测试题上，原方案 nDCG@5 为 0.2455，重排方案为 0.2905；直接关键词题分别为 0.6498、0.6692。
4. 48 道测试题中，重排相对原方案 17 题提升、19 题持平、12 题下降。以主题为簇进行 2000 次配对 Bootstrap，nDCG 差值的 95% 区间约为 **[-0.0227, 0.0968]**，跨过 0。样本不支持“统计显著提升”的宣传。
5. 8 道无答案题中，词汇检索均未返回候选，其余方案均返回候选。**返回近邻不代表存在有效证据，更不等于 Agent 已幻觉作答**；目前不能用向量分数替代证据充分性判断。

## 3. 定位到的问题与改进

### 已完成的改进

- 将真实多语言嵌入模型作为独立可选 Provider，384 维归一化向量，CPU 本地推理，不调用付费生成模型。
- 固定默认模型权重 revision，并纳入 embedding signature；索引、查询依赖同一签名，避免把 Hash 和真实语义空间混用。
- 加入可选 Cross-Encoder，对最多 40 个候选知识块做 query–document 联合评分；保留快速规则模式。
- 检索缓存区分重排模式和模型名称；返回实际重排标记与分数。直接请求语义重排失败时返回明确错误，不悄悄伪装成成功。
- Agentic RAG 也可选择 Cross-Encoder；其已有降级链会显式记录重排失败，而不是丢失原因。
- 增加逐题输出、分问法分析、胜负案例、置信区间和模型/环境参数记录。

### 仍然存在的限制

- 小型通用模型不一定理解招聘技能的细粒度区别。真实向量单路对 `Redis`、`Function Calling/MCP` 等精确术语检索出现明显回退，应保留词汇通道。
- 当前嵌入模型默认最大序列长度为 **128 tokens**。V3 已把单块软上限控制在 110 个保守估算 token，并以句子/分句为边界拆分；仍需在人工金标上比较段落窗口聚合和更长上下文中文模型。
- Cross-Encoder 前置候选池只有 40 块；召回缺失不能靠重排修复。池大小、岗位去重和多样性约束也可能影响 Recall。
- 标注主要来自技能词命中，天然偏向术语匹配；没有区分“核心要求”“加分项”“仅背景提及”。无答案题偏容易且问法部分人工化。需要独立人工复核、真实用户问题和贴近业务的 hard negatives。
- SQLite 词汇回退 **不是 PostgreSQL FTS，也不是 BM25**。本表不能当作 PostgreSQL 线上延迟或线上 A/B 结果。上线决策前应补同规模 PostgreSQL 数据库评测和并发负载测试。
- 本次评测检索，不评测生成回答。没有回答准确率、幻觉率、Token 降幅或用户满意度的实测结论。

案例（完整岗位 ID 和结果见 `analysis.json`）：

- 提升：“语音识别与语音合成岗位”，nDCG 增量 +0.6131。
- 提升：“哪些工作涉及把说话声音转成文字或者反过来”，+0.3869。
- 回退：“模型评测与评测集构建岗位”，-0.5296。
- 回退：“自然语言处理 NLP 岗位”，-0.3452。

**发布决策：**提供真实模型与重排的可选配置，保留现有默认策略，不在缺乏人工金标和延迟预算时自动替换线上索引。高质量查询可启用重排，日常查询仍可走快速模式。

## 4. V3 切块优化复验

V3 针对首轮实验暴露的问题做了三项改动：按 110 个保守估算 token 控制块长；技能块同时保留“必备/加分”强度和对应原文证据；结构化抽取未覆盖的 JD 原文进入低权重 `source_context`，避免解析遗漏导致知识永久丢失。切块在规范化和别名展开后再次去重，解决 `Torch` / `PyTorch` 等别名映射到相同内容时的重复键问题。

复验严格复用了 V2 的 120 个岗位快照、80 道问题、标签和拆分，语料 SHA-256 均为 `2e2e46d020b26c511c632ecb570e5c97339ac8c8182ed4d543f133f02410c6ef`。唯一主要变量是知识切块由 V2 的 545 块变为 V3 的 1245 块。

| 方案 | V2 Recall@5 | V3 Recall@5 | V2 nDCG@5 | V3 nDCG@5 | V2 MRR@5 | V3 MRR@5 | V2 P95 | V3 P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 词汇检索 | 0.0979 | 0.0952 | 0.2487 | 0.2455 | 0.2604 | 0.2604 | 86.7 ms | 105.9 ms |
| Hash 混合检索＋规则重排 | 0.1749 | 0.1798 | 0.4477 | 0.4650 | 0.5538 | 0.5677 | 241.6 ms | 295.6 ms |
| 真实语义向量单路 | 0.1227 | 0.1943 | 0.2919 | 0.4070 | 0.4372 | 0.5479 | 240.8 ms | 395.0 ms |
| 真实语义混合检索＋规则重排 | 0.1915 | 0.2140 | 0.4303 | 0.4866 | 0.5493 | 0.6229 | 301.4 ms | 477.0 ms |
| 真实语义混合检索＋Cross-Encoder | 0.1826 | **0.2692** | 0.4798 | **0.5844** | 0.6361 | **0.7715** | 5269.1 ms | **1009.0 ms** |

结论：V3 配合 Cross-Encoder 时，Recall@5 相对提高约 **47.4%**，nDCG@5 相对提高约 **21.8%**，MRR@5 相对提高约 **21.3%**，P95 延迟降低约 **80.9%**。不使用 Cross-Encoder 的语义混合方案也提升了质量，但由于候选块增多，P95 从 301.4 ms 上升到 477.0 ms；这是后续需要通过候选裁剪、批量向量化和 PostgreSQL 线上压测继续优化的成本。

生产库已完成 V3 回填：历史回填任务 803/803 成功；验收时 837 个有效岗位对应 837 个 V3 文档、16,332 个知识块，最大估算 token 为 110、P95 为 108，重复内容键为 0。新增岗位已继续通过增量任务进入知识库。

本次复验仍使用 silver 标注，且只证明检索排序改善，不代表最终生成回答的事实忠实度已经得到证明。无答案查询中语义方案仍会返回近邻，需要继续依赖证据充分性判断与回答层拒答机制。

## 5. 证据充分性与 Agent 路由优化

在 V3 基础上，Agentic RAG 增加了两层保护：

- V3 的 `source_context` 现在会参与技能、职责、学历、经验、薪资、学习路线和比较问题的检索，结构化抽取遗漏的原文不会在 Agent 查询中被跳过。
- `EvidenceEvaluator` 增加最高直接相关性门槛。即使候选岗位覆盖了某个章节，只要最高证据相关性低于 `RAG_EVIDENCE_MIN_RELEVANCE`（默认 0.42），就不会标记为 `answerable=true`，同时返回“语义近邻不能视为确定答案”的警告。

接口会返回 `max_relevance_score`，并在 Agent trace 的 `evidence_max_relevance` 中记录实际值，便于前端展示和线上调参。该门槛只影响“证据是否足够”的判定，不会删除原始召回结果，也不会改变已经稳定的快速检索排序。

## 6. Worker：实际测试了什么

实现使用 PostgreSQL 持久化队列，不是 API 进程内的 `asyncio.create_task` 占位 Worker。排名和知识库索引由独立 `python -m app.worker` 执行；浏览器投递、聊天流和其他 Agent 任务不在此次迁移范围。

| 故障/竞争场景 | 验证断言 |
| --- | --- |
| 事务回滚与重复入队 | 回滚不留下任务；相同 kind/run_id 只有一条队列记录 |
| 两个 Worker 同时竞争 | 同一任务只有一个执行者，另一个取不到锁 |
| 业务完成、队列确认丢失 | 再次领取不重复业务效果 |
| 执行中取消 | 旧写入不能覆盖 CANCELLED 状态 |
| 子进程被强制 kill | 新 Worker 读取已提交检查点，第一步效果仍为一次 |
| 真实知识索引业务恢复 | RUNNING 明细恢复执行，完成计数与队列终态正确 |
| 取消后立即重试 | generation 变化后，旧 Worker 的 flush/commit 被拒绝 |
| 丢失数据库 advisory lock | 失去所有权后不能提交成功状态 |
| 超过恢复次数 | 达到 5 次领取上限后失败，不无限运行 |
| 真实排名业务恢复 | 复用原有评分 ID，cache_hits=1，未增加 LLM 调用 |

最终部署依赖环境中运行 **171 passed，0 skipped**，包含 **10 项真实 PostgreSQL Worker 用例**；还验证了恢复次数耗尽后关联计划进入 FAILED，不再卡在 RANKING。测试在 `careerpilot_eval` 隔离 PostgreSQL 数据库内运行，每个用例新建独立 schema，结束后只清理自己的测试 schema。杀进程测试只终止测试子进程，没有终止用户任务。最后测试结果以 XML 证据为准。

可靠性边界：这是 **at-least-once 执行＋幂等落库/检查点**，不是对远程 LLM 或招聘网站副作用的 exactly-once 承诺。若外部调用已完成但结果尚未提交，恢复时可能再次调用；本轮没有付费调用。知识索引全局串行写入以避免不同回填任务竞争同一岗位；不宣称无限水平扩展。事务模式 PgBouncer 不适用于这里的 session advisory locks。
